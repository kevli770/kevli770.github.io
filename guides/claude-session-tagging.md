# Claude Code Session Tagging: איך לגרום לשני סשנים של Claude Code לדבר אחד עם השני

> אם אתם רוצים להמשיך את אותה השיחה בטרמינל אחר, זה לא הפיצ'ר הנכון, שם צריך פשוט לעשות resume לסשן. שלוש פקודות ואתם בפנים.

מאת קווין ליאקס. פורסם 2026-08-15. נושא: Claude ו-Claude Code.
העמוד המלא: https://kevli770.github.io/guides/claude-session-tagging

## מה זה בכלל

עד היום כל סשן של Claude Code חי בבועה משלו. פתחתם שני טרמינלים, אחד עובד על ה-backend והשני על ה-frontend, ואם משהו שקרה באחד היה רלוונטי לשני, הייתם צריכים להעתיק ידנית את ההסבר מטרמינל אחד לשני.

החל מגרסה `v2.1.224` (שיצאה ב-7 באוגוסט 2026) יש פיצ'ר שנקרא **Cross-Session Messaging**, והוא מאפשר לסשן אחד לשלוח הודעת טקסט לסשן אחר. אתם כותבים שטרודל, בוחרים את שם הסשן, ושולחים לו משימה. בדיוק כמו לתייג עובד בסלאק.

חשוב להבין מה עובר ומה לא: עוברת **רק הודעת טקסט** שקלוד כותב בעצמו. לא עוברת היסטוריית שיחה, לא עוברים קבצים ולא עובר קונטקסט. אם אתם רוצים להמשיך את אותה השיחה בטרמינל אחר, זה לא הפיצ'ר הנכון, שם צריך פשוט לעשות resume לסשן.

## הכל בדקה: התקציר

שלוש פקודות ואתם בפנים. פותחים שני טרמינלים בשתי תיקיות שונות ומריצים:

**בטרמינל הראשון:**

```bash
claude --name api-worker
```

**בטרמינל השני:**

```bash
claude --name frontend
```

**עכשיו בכל אחד מהם תבדקו מי זמין:**

```
/peers
```

**ומכאן פשוט מתייגים בתוך הפרומפט:**

```
tell @api-worker that the schema migration is done
```

זהו. אין מה להתקין ואין מה להפעיל בהגדרות. אם הגרסה שלכם מספיק חדשה ואתם על Mac או Linux, זה כבר עובד.

## מה צריך כדי שזה יעבוד

| דרישה | פירוט |
|---|---|
| **גרסה** | 2.1.224 ומעלה. לתיוג עם שטרודל צריך 2.1.232 ומעלה. בודקים עם claude --version |
| **מערכת הפעלה** | macOS ו-Linux בלבד, כולל Linux בתוך WSL 2. בטרמינל Windows רגיל הפיצ'ר לא קיים |
| **ספק** | לא זמין דרך Amazon Bedrock, Claude Platform on AWS, Google Cloud Agent Platform או Microsoft Foundry |
| **משתני סביבה** | אם כיביתם טלמטריה הפיצ'ר נכבה איתה. בדקו שאין לכם DISABLE\_TELEMETRY, DO\_NOT\_TRACK, DISABLE\_GROWTHBOOK או CLAUDE\_CODE\_DISABLE\_NONESSENTIAL\_TRAFFIC |
| **אותה מכונה** | שני הסשנים חייבים לראות את אותה מערכת קבצים. סשן בתוך קונטיינר וסשן על המארח לא יראו אחד את השני |

**משתמשי Windows: שימו לב**

בטרמינל Windows רגיל (PowerShell או CMD) פשוט לא יקרה כלום, הפקודה `/peers` אפילו לא תזוהה. הפתרון הוא להריץ את שני הסשנים בתוך WSL 2, ואז זה עובד בדיוק כמו על Linux.

## שלב 1: לתת שם לסשן

הכתובת של סשן היא השם שלו. אם לא תיתנו שם, Claude Code ייתן אחד לבד לפי שם התיקייה שאתם עובדים בה, למשל `my-app-3f` בתיקייה בשם my-app. זה עובד, אבל שמות שאתם בוחרים קלים בהרבה לתיוג.

### אפשרות א: להתחיל עם שם

```bash
claude --name api-worker
```

### אפשרות ב: לשנות שם באמצע העבודה

```
/rename api-worker
```

אם תבחרו שם שכבר תפוס על ידי סשן חי אחר, Claude Code ישאיר את השם אצל מי שכבר החזיק בו וייתן לכם וריאציה. עדיין ייתכנו מקרים שבהם שני סשנים חולקים שם, ואז Claude Code מוסיף מזהה קצר לכל שורה ומשתמש בו בכתובת. בכל מקרה מוצגת גם תיקיית העבודה של כל סשן, כדי שתדעו להבדיל ביניהם.

## שלב 2: לראות מי זמין

שכחתם איך קוראים לסשן השני? יש פקודה בדיוק בשביל זה:

```
/list-agents
```

או הקיצור, שהרבה יותר נוח לזכור:

```
/peers
```

הרשימה שתקבלו מכילה ארבעה סוגים של יעדים:

- סאב-אייג'נטים שרצים בתוך הסשן הנוכחי
- סשנים מקומיים אחרים על אותה מכונה, כולל סשנים שרצים ברקע
- סשנים בענן של Claude Code on the web, מסומנים בתווית cloud
- סשנים על מכונות אחרות שלכם, מסומנים בתווית Remote Control

שתי הקטגוריות האחרונות מופיעות רק אם הסשן הנוכחי מחובר ל-Remote Control. אם `/peers` בכלל לא מזוהה כפקודה, סימן שהפיצ'ר לא זמין אצלכם, ושווה לחזור לטבלת הדרישות למעלה.

## שלב 3: לשלוח הודעה

יש שתי דרכים, ושתיהן פשוט פרומפט רגיל שאתם כותבים לקלוד. אתם אף פעם לא מפעילים כלי בעצמכם.

### דרך א: בלי לתייג, קלוד בוחר את היעד

פשוט מתארים מה אתם רוצים שהסשן השני יידע או יעשה, וקלוד מוצא אותו לבד:

```
ask the session in my other terminal whether the migration finished
explain what we just changed to the session working on the payments API
```

### דרך ב: תיוג מפורש עם שטרודל

כותבים `@` ואת האותיות הראשונות של שם הסשן, ובוחרים מהרשימה שנפתחת. בדיוק כמו שמתייגים סאב-אייג'נט:

```
let @api-worker know the schema migration finished
```

שימו לב לפרט קטן שמבלבל: הרשימה נפתחת רק אחרי שהקלדתם **לפחות אות אחת** אחרי השטרודל. על שטרודל ריק לא יופיעו שורות של סשנים. אפשר גם פשוט להקליד את השם בלי הרשימה. אם יותר מסשן אחד עונה לשם שתייגתם, קלוד ישאל אתכם למי התכוונתם לפני ששולח.

### מה קורה מתחת למכסה המנוע

קלוד משתמש בשני כלים: `ListAgents` כדי לגלות למי הוא יכול להגיע, ו-`SendMessage` כדי למסור את ההודעה לפי שם. את נוסח ההודעה עצמו קלוד מנסח בעצמו, ולכן הפרומפט שלכם יכול להיות כללי לגמרי. הוא גם לא חייב שתבקשו: אם קלוד מזהה ששינוי שהוא בדיוק עשה משפיע על מה שסשן אחר בונה, הוא יכול לשלוח הודעה מיוזמתו.

## איך ההודעה נראית בצד השני

ההודעה מופיעה בשיחה של הסשן המקבל תחת השם של השולח, ונשארת שם. הטיימינג עובד ככה:

- אם הסשן המקבל באמצע תור עבודה, ההודעה נקראת בין קריאות כלים. כלי שרץ אף פעם לא נקטע באמצע
- אם הסשן המקבל בטל ולא עושה כלום, Claude Code פותח איתה תור חדש מיד

כך זה נראה בפועל אצל המקבל, וזה הכל, רק הטקסט הזה, בלי היסטוריה ובלי קבצים:

```
Schema migration finished: the new column is tenant_id, and rebasing on main is safe now.
```

שימו לב שהודעה שנמסרה נספרת בשימוש שלכם בדיוק כמו פרומפט שאתם מקלידים. המקבל יכול גם להשיב לשולח באותה הדרך.

## אבטחה: מה הודעה מסשן אחר לא יכולה לעשות

זו הנקודה הכי חשובה במדריך, וזו גם הסיבה שאפשר להשתמש בזה בלב שקט. Claude Code מודיע לסשן המקבל שההודעה הגיעה מסשן אחר ולא מכם, ומגביל אותה:

| ההגבלה | מה זה אומר |
|---|---|
| **לא מאשר הרשאות** | הודעה מסשן אחר לעולם לא נחשבת להסכמה שלכם, ולא יכולה לענות במקומכם על בקשת הרשאה שממתינה |
| **לא משנה הגדרות** | קלוד המקבל מונחה לא לשנות הגדרות הרשאות, לא את CLAUDE.md ולא קונפיגורציה אחרת רק כי סשן אחר ביקש |
| **פקודות לא רצות** | פקודת סלאש בתוך טקסט ההודעה מגיעה כטקסט רגיל בלבד ולא מורצת אף פעם |
| **ההרשאות עדיין נשאלות** | אם הפעולה שנדרשת מההודעה מצריכה הרשאה שאין לסשן, תקבלו בדיוק את אותה בקשת אישור כמו בכל עבודה אחרת |

**במילים אחרות: הסשן שמקבל את ההודעה הוא סוג של עמית ולא מפתח ראשי.**

גם בכיוון השני יש גבול: קלוד מונחה לא לבקש מסשן אחר פעולה שנדחתה או נחסמה אצלו, או כזו שההגדרות שלו היו חוסמות, אלא להחזיר את זה אליכם.

## לאן ההודעה נוסעת

שאלה שכולם שואלים: האם ההודעה עוברת דרך השרתים של Anthropic? התשובה תלויה איפה נמצא הסשן השני.

| איפה הסשן השני | איך ההודעה נוסעת |
|---|---|
| **על אותה מכונה** | דרך סוקט מקומי לכל סשן. לעולם לא עוברת דרך השרתים של Anthropic |
| **על מכונה אחרת שלכם** | דרך השרתים של Anthropic, ומגיעה בחיבור ה-Remote Control של אותה מכונה |
| **ב-Claude Code on the web** | דרך השרתים של Anthropic ישירות לסשן בענן |

הסוקט המקומי מוגבל למשתמש מערכת ההפעלה שלכם, כך שבמכונה משותפת סשנים של משתמש אחר לא יכולים להגיע אליו. את הכתובת עצמה אפשר לראות בשורה `Peer address` של הפקודה `/status`.

רוצים לוודא שכלום לא יוצא מהמכונה בלי אישור שלכם? הוסיפו את זה להגדרות:

```json
{
  "isolatePeerMachines": true
}
```

עם ההגדרה הזו קלוד יבקש את אישורכם המפורש לפני שכל הודעה יוצאת אל מעבר למכונה, גם במצב שמדלג על בקשות הרשאה רגילות. הודעות בין סשנים על אותה מכונה לא מפעילות את הבקשה הזו.

## שליטה בהודעות שנכנסות אליכם

ההגדרה `crossSessionInbound` קובעת מה סשן עושה עם הודעות שמגיעות מהסשנים האחרים שלכם:

| ערך | התנהגות |
|---|---|
| `accept` | כל הודעה נמסרת לקלוד |
| `hold` | מוצגת התראה על כל הודעה והיא לא נמסרת. אם בהמשך תחול הגדרת accept, ההודעות שהוחזקו משתחררות |
| `refuse` | כל הודעה נזרקת בלי להימסר |

אפשר לבחור את הערך גם מתוך `/config` בשורה **Messages from your other sessions** (דורש גרסה 2.1.232 ומעלה).

אם לא הגדרתם כלום, ההחלטה מתקבלת לפי מצבי ההרשאות של שני הסשנים. הכלל בגדול: סשן שמדלג על בקשות הרשאה נחשב מסוכן יותר, ולכן סשן רגיל שמקבל הודעה מסשן כזה יחזיק אותה לאישורכם. דיאלוג אישור שנשאר בלי מענה נסגר אחרי חמש דקות כברירת מחדל וההודעה נזרקת.

## לכבות את זה לגמרי

קבלה ושליחה הן שתי בקרות נפרדות. כדי להפסיק לקבל, מגדירים `refuse`. כדי להפסיק לשלוח ולרשום, מוסיפים חוקי דחייה על שני הכלים:

```json
{
  "permissions": {
    "deny": ["SendMessage", "ListAgents"]
  },
  "crossSessionInbound": "refuse"
}
```

שתי הערות חשובות: דחייה של `SendMessage` מבטלת גם שליחת הודעות לסאב-אייג'נטים ולחברי צוות אייג'נטים, כי זה אותו כלי בדיוק. וגם, סשן שדוחה הודעות לא מראה שום סימן חיצוני לכך, לא ב-`/status` שלו ולא ברשימות של סשנים אחרים, אז אם משהו לא מגיע, בדקו את הקונפיגורציה שלו ישירות.

## כשמשהו לא עובד

- הפקודה peers לא מזוהה בכלל: הפיצ'ר לא זמין בסשן הזה. התחילו מ-claude --version ועברו על טבלת הדרישות
- הפקודה עובדת אבל ההודעה לא הגיעה: יש משהו צר יותר שחוסם. בדקו חוקי דחייה, ובדקו את הגדרות הקבלה של הסשן המקבל
- סשן שאתם מצפים לו לא ברשימה: סשן מופיע רק אם הוא קשר סוקט תיבת דואר. סשן שהופעל במצב bare לא קושר סוקט ולכן לא יופיע
- סשן בענן לא מופיע: הוא מופיע רק כשהסשן הנוכחי מחובר ל-Remote Control
- סשן במכונה אחרת לא מופיע: הוא מופיע רק אם הוא רץ עם Remote Control וגם הסשן שלכם מחובר
- סשן בקונטיינר לא רואה את המארח: זה מתוכנן, לקונטיינר יש מערכת קבצים משלו. שני סשנים בתוך אותו קונטיינר כן ידברו

## מגבלות שכדאי להכיר

- טקסט בלבד. לא עוברים קבצים, לא היסטוריה ולא קונטקסט. רק מה שקלוד ניסח
- לולאות הודעות מווסתות. יש הגבלת קצב לכל שולח, כפילויות זהות שמגיעות בטווח קצר נזרקות, ויש תקרה של 50 הודעות שממתינות לקריאה בכל סשן. לולאה בין שני סשנים נעצרת מעצמה
- מקסימום 100 הודעות מוחזקות בו זמנית. מעבר לזה הישנות ביותר נזרקות
- בסשן שרץ עם הדגל p- אין דיאלוג אישור. הודעה שהוחזקה נשמרת חמש דקות ואז נזרקת, אלא אם הגדרתם אחרת

## טיפים מהשטח

- תנו שמות לפי תפקיד ולא לפי טכנולוגיה. api-worker ו-migration-runner קלים לתיוג הרבה יותר מ-node-1 ו-node-2
- השימוש הכי משתלם הוא worktrees מקבילים על אותו ריפו. כשמשהו נוחת בענף אחד, הסשן שם מודיע לאחרים במקום שתגלו את זה בקונפליקט
- משימה ארוכה כמו מיגרציה או ריצת טסטים? תנו לסשן שמריץ אותה לדווח בחזרה לסשן שאתם צופים בו, במקום לשבת ולבהות בטרמינל
- אפשר גם לשאול מהצד השני, ולא רק לחכות שידווחו לכם. פשוט בקשו מקלוד לשאול את הסשן השני אם הוא סיים
- לסשן שרץ בלי השגחה עם הדגל p-, הפעילו accept דרך הדגל settings-- שלו ולא בהגדרות המשתמש, כדי שזה לא יחול על כל סשן שאתם מריצים
- אם אתם על Windows, הריצו את שני הסשנים בתוך אותה הפצת WSL 2. שתי הפצות שונות הן שתי מערכות קבצים שונות
- רוצים ודאות שכלום לא יוצא מהמכונה? isolatePeerMachines בערך true, וזהו
