# Skill Doctor: ה-Skill שבודק את ה-Skills שלכם ומתקן את מה שלא עובד

## מה זה Skill Doctor

Skill Doctor הוא כלי קוד פתוח שבן הולמס (Ben Holmes) מ-Warp שחרר, והוא עושה דבר אחד: קורא את שיחות העבודה האמיתיות שלכם עם סוכן הקוד, נותן להן ציון, ומזהה מה חוזר על עצמו ונכשל.

**במקום שתנחשו איך לשפר את ההוראות או ה-skills של הסוכן, הוא נשען על מה שבאמת קרה, ומציע לכם את השינוי עצמו כ-diff מוכן.**

הכל רץ מקומית. הטרנסקריפטים לא נשלחים לשום מקום. הדבר היחיד שניתן לשתף הוא דוח ה-HTML שאתם בוחרים לפרסם.

## הבעיה שהוא פותר

בכל פעם שהסוכן טועה, אתם מתקנים אותו בתוך הצ׳אט: לא ככה, תשתמש בפונקציה הזאת. אצלנו בפרויקט לא כותבים קוד בצורה הזאת. הוא מתקן, אתם ממשיכים לעבוד, ואז השיחה נגמרת.

הלקח נשאר קבור בתוך אותה שיחה, ובפרויקט הבא תצטרכו להגיד את אותו הדבר מחדש. Skill Doctor סוגר את הלולאה הזאת: התיקונים שלכם הופכים להוראות שהסוכן יקבל בפעם הבאה.

## איך הוא עובד: שלושה שלבים

![שלושת השלבים כפי שהם מופיעים באתר הרשמי של Warp](https://kevli770.github.io/_astro/01.Yic6O87R.jpg)

*שלושת השלבים כפי שהם מופיעים באתר הרשמי של Warp*

- Aggregate: אוסף טרנסקריפטים של שיחות עבודה אמיתיות מהמחשב שלכם
- Score: נותן לכל שיחה ציון לפי שתי אמות מידה: efficiency ו-code quality
- Improve: מזהה דפוסים בשיחות שנכשלו, ומנסח מהן שינוי קונקרטי ל-skill

## מה צריך לפני שמתחילים

- אחד משלושת הסוכנים הנתמכים: Claude Code, Codex או Warp
- python3 מותקן: סקריפטי האיסוף והרינדור כתובים בפייתון
- היסטוריית שיחות מקומית מהתקופה האחרונה (ברירת המחדל: 45 יום אחורה)
- node ו-npx, בשביל פקודת ההתקנה

## איך מתקינים

ההתקנה היא פקודה אחת. בוחרים את הסוכן שלכם בדגל agent--:

### התקנה גלובלית (בכל הפרויקטים)

עבור Claude Code:

```bash
npx skills@latest add warpdotdev/common-skills --skill skill-doctor --agent claude --global
```

עבור Codex:

```bash
npx skills@latest add warpdotdev/common-skills --skill skill-doctor --agent codex --global
```

עבור Warp:

```bash
npx skills@latest add warpdotdev/common-skills --skill skill-doctor --agent warp --global
```

### לראות את כל ה-skills שיש ברפוזיטורי

```bash
npx skills@latest add warpdotdev/common-skills --list
```

### לעדכן אחרי שהתקנתם

```bash
npx skills@latest update --global --agent claude
```

אפשר גם פשוט להעתיק את התיקייה של הסקיל מהרפוזיטורי לתוך התיקייה agents/skills. בפרויקט שלכם.

## איך מריצים

פותחים את הסוכן בתיקיית הפרויקט, ומריצים:

```
/skill-doctor
```

הוא ישאל אתכם שתי שאלות לפני שהוא נוגע בכלום:

### שאלה 1: אילו שיחות לדרג

- שיחות ברפוזיטורי הזה: מומלץ, וזאת ברירת המחדל כשאתם בתוך פרויקט
- כל השיחות: סריקה רחבה על כל מה שיש במחשב
- בחירת פרויקטים: נותנים לו רשימת נתיבים, והוא מפיק דוח אחד משולב

### שאלה 2: אילו skills להעריך

- skills של הפרויקט יחד עם הגלובליים, מומלץ
- skills של הפרויקט בלבד

**אחרי שתי התשובות הוא ממשיך לבד. הוא לא כותב שום דבר לתוך הרפוזיטורי שלכם, כל התוצרים נכתבים לתיקייה זמנית שהוא יוצר לעצמו.**

## הדגלים השימושיים

אלה דגלים של סקריפט האיסוף. הם שימושיים במיוחד כשהריצה הרגילה לא מצאה מספיק שיחות:

| דגל | מה הוא עושה |
|---|---|
| `--days N` | כמה ימים אחורה לסרוק. ברירת המחדל 45: הגדילו אם לא נמצאו מספיק שיחות |
| `--max-sessions N` | תקרת שיחות לדגימה. ברירת המחדל 12 |
| `--repo PATH` | להוסיף פרויקט לדוח. אפשר לחזור על הדגל כמה פעמים |
| `--all-conversations` | לא לסנן שיחות לפי פרויקט |
| `--include-global-skills` | לדרג גם את הסקילים הגלובליים ולא רק את אלה של הפרויקט |
| `--harness VALUE` | להגביל למקור אחד: claude, codex או warp. ברירת המחדל auto סורקת הכל |
| `--include-subagents` | לכלול גם שיחות של תתי-סוכנים |

## איך הוא נותן ציון

שתי אמות מידה, ולכל אחת טבלת ציונים קבועה. זה לא ציון שרירותי: זה מיפוי מפורש מתווית למספר.

### Efficiency: כמה ישר הסוכן הלך למטרה

| תווית | ציון | מתי |
|---|---|---|
| `highly_efficient` | **1.0** | מסלול ישיר. שום דבר לא נקרא או הורץ פעמיים, שום עבודה לא נעשתה מחדש |
| `mostly_efficient` | **0.8** | מעידה אחת או שתיים: קריאה כפולה, ניסיון חוזר מוקדם, בלי מחיר המשך |
| `mostly_inefficient` | **0.4** | בזבוז חוזר, או סבב תיקונים שבדיקה מוקדמת היתה מונעת |
| `highly_inefficient` | **0.2** | הבזבוז שלט בריצה: אותו פגם חוזר, תיקון חוזר מצדכם, או התרוצצות ממושכת |

### Code Quality: האם הקוד עצמו היה עובר ריוויו

| תווית | ציון | מתי |
|---|---|---|
| `approve` | **1.0** | מתכנת בכיר היה מאשר את זה כמו שזה, עם הערות שוליים לכל היותר |
| `block` | **0.2** | לפחות פגם אחד שמישהו היה דורש לתקן לפני מיזוג, באג, מקרה קצה שהוחמץ, בדיקות חסרות |
| `insufficient_evidence` | **0.5** | לא היה diff בשיחה, או שלא נראה ממנו מספיק כדי לשפוט. השיחה מוחרגת מהממוצע |

### איך זה מצטרף לציון הסופי

הממוצעים הגולמיים עוברים עקומה שמותחת אותם לטווח של ציון אות:

```
curve(score) = 0.5 + 0.5 * score
```

ואז מתחשבים במשקלים:

```
overall = 0.5*efficiency + 0.35*code_quality + 0.15*skill_coverage
```

המדד skill\_coverage הוא אחוז השיחות שבהן לפחות סקיל אחד שמותקן אצלכם באמת נכנס לפעולה. אם אין לכם סקילים בכלל, הוא אפס, והדוח הופך לנימוק למה כדאי להתחיל.

## איך לקרוא את הדוח

בסוף הריצה נפתח בדפדפן קובץ HTML אחד עצמאי. יש בו שלושה חלקים.

### 1. כרטיס הציונים

![דוח לדוגמה מהאתר הרשמי: ציון כולל, ולצידו שלושת המדדים בנפרד](https://kevli770.github.io/_astro/02.C8eh1JUm.jpg)

*דוח לדוגמה מהאתר הרשמי: ציון כולל, ולצידו שלושת המדדים בנפרד*

ציון אות כולל, ולידו שלוש השורות: efficiency, code quality ו-skill coverage. השורה הכי נמוכה היא זו שכדאי לטפל בה קודם.

### 2. שלושת הממצאים

שלושה דפוסים קונקרטיים שחזרו על עצמם, לא עצות כלליות. הם מגיעים רק מהשיחות שנחשבות נכשלות, שיחה שבה לפחות ציון אחד ירד מתחת ל-0.5.

### 3. השינויים המוצעים

![שינוי מוצע, מוצג כ-diff עם השורה שיוצאת והשורה שנכנסת](https://kevli770.github.io/_astro/03.D9iKKXN8.jpg)

*שינוי מוצע, מוצג כ-diff עם השורה שיוצאת והשורה שנכנסת*

לכל הצעה יש שם של סקיל, משפט אחד שמסביר את השינוי, וההוכחה, איזו שיחה ואיזה רגע בתוכה הצדיקו אותו. ה-diff עצמו מוצג לצד ההצעה, ואפשר לפתוח אותו.

**חשוב: בשלב הזה הוא לא נוגע בקבצי הסקילים האמיתיים שלכם. הגרסאות המוצעות נכתבות לתיקייה נפרדת, ואתם מחליטים מה להחיל.**

## טיפים

- אל תריצו את זה על פרויקט חדש. תריצו על הפרויקט שבו כבר רבתם עם הסוכן עשרות פעמים, שם נמצא הדאטה המעניין
- אם הוא אומר שלא נמצאו שיחות, הגדילו את מספר הימים מעבר ל-45 או בחרו פרויקטים אחרים
- בריצה ראשונה בחרו את השיחות של הרפוזיטורי הנוכחי, דוח ממוקד קל יותר לפעולה מדוח על כל המחשב
- סקיל שמותקן אצלכם ומעולם לא נכנס לפעולה בשיחה שנכשלה הוא כמעט תמיד בעיית תיאור, לא בעיית תוכן
- התחילו מהמדד הנמוך ביותר בכרטיס. אם code quality גבוה ו-efficiency נמוך, הבעיה היא בתהליך ולא בקוד
- החילו הצעה אחת בכל פעם, והריצו שוב אחרי כמה ימי עבודה, ככה רואים אם השינוי באמת עזר
- הדוח הוא קובץ אחד עצמאי, ויש בו כפתור שמייצא ממנו תמונה מקומית אם בא לכם לשתף

## מגבלות שכדאי להכיר

- נתמכים שלושה סוכנים בלבד: Warp, Claude Code ו-Codex. בכל סוכן אחר הוא עוצר לפני שהוא קורא משהו
- הוא מזהה את הסוכן מהקשר הריצה, לא מהקבצים שהוא מוצא בדיסק
- המדד code quality מדורג רק בשיחות שבהן באמת נכתב קוד. בלי diff הוא רושם insufficient\_evidence
- השינויים המוצעים נוגעים לסקילים של הפרויקט, לא לגלובליים
- ההצעות נשענות רק על כשלונות שנצפו בפועל, לא על שיטות עבודה מומלצות באופן כללי
